# 本地 Codex CLI 工作流验证模式设计

## 目标

在不改变统一视频工作台页面、不恢复用户可见执行方式开关、也不削弱生产安全边界的前提下，为本地开发环境增加 Codex CLI 多模态执行器。开发者可以用真实 Codex 登录态验证“阶段启动 → 队列 → 运行 → 质量门 → 审核 → 应用 → 下游解锁”的完整工作流；分镜提示词生成必须同时理解当前镜头的参考图片，而不是只读取图片名称或文本描述。上线前和生产部署始终使用后台文本 API / 云端 Worker。

Codex CLI 替代导演与美术等文本 Agent 的上游调用，并在分镜提示词阶段通过多图输入完成图文联合理解。视频生成仍使用后台发布的视频渠道；素材加白和对象存储不由 Codex CLI 模拟。本轮真实验收允许在预检通过后提交一次最低消耗企业视频任务。

## 方案选择

采用环境自动隔离，不在页面或后台模型设置中提供手动切换。

- 本地宿主机显式设置 `WORKFLOW_TEXT_EXECUTOR=codex-cli` 与 `WORKFLOW_LOCAL_CODEX_ENABLED=true` 后启用 Codex CLI。
- 默认值和正式部署固定为 `WORKFLOW_TEXT_EXECUTOR=api`、`WORKFLOW_LOCAL_CODEX_ENABLED=false`。
- `APP_ENV`、`GIN_MODE`、`GO_ENV` 或 `NODE_ENV` 任一表示 `production` / `release` 时，只要检测到 CLI 执行器或本地开关，服务启动立即失败。
- 正式 Docker 配置继续显式写入 API 模式，镜像不安装 Codex CLI，形成配置校验、运行时代码和镜像内容三重门禁。

不采用页面手动切换，因为它会把开发能力暴露给普通用户并增加误上线风险；也不维护两套工作流页面，因为状态、审核与应用逻辑会产生分叉。

## 架构

### 1. 统一执行器边界

在 Go Worker 内抽出负责文本与可选图片输入的执行器接口。队列领取、租约续期、取消、重试、阶段状态、artifact、质量门、人工审核、应用回执和事件记录继续使用现有实现，不因上游不同而分叉。

执行器提供两种实现：

- API 执行器：封装当前模型渠道选择、OpenAI 兼容请求、重试分类和计费逻辑。
- Codex CLI 执行器：在宿主机启动 `codex exec`，读取当前 Codex 登录态，根据任务附加受控图片，将最终文本转换为现有 `agentRunCallResult`。

`AgentRun` 新增 `Executor` 审计字段，值为 `api` 或 `codex-cli`。任务创建时写死执行器类型，排队后即使环境变量变化也不会改走另一条通道。

### 2. CLI 调用方式

CLI 执行器只接受 Worker 已生成的系统提示词和用户提示词，不接受浏览器传入的命令、工作目录或额外参数。调用形式固定为：

```text
codex exec --ephemeral --sandbox read-only --color never
  --cd <服务端固定工作目录>
  --output-last-message <受控临时文件>
  [-i <受控暂存图片>]...
  [--model <服务端可选模型>]
  -
```

- Prompt 通过标准输入传入，避免 shell 拼接和参数注入。
- 使用 `exec.CommandContext`，停止任务或服务退出时终止子进程。
- 使用临时目录保存最终消息，读取后立即删除；stdout / stderr 只保留限制长度的诊断，不写入密钥或完整环境变量。
- 固定 `read-only` 与 `--ephemeral`，不允许 CLI 修改代码、工作流文件或用户素材。
- 工作目录只来自 `WORKFLOW_CODEX_WORKDIR` 或服务启动目录，不接受项目、分集或请求参数覆盖。
- 图片参数只来自当前 Agent Run 的受控暂存清单，不接受浏览器传入的路径；最多 9 张，并保持角色、场景、道具的选定顺序。
- CLI 默认单并发，超时沿用 Agent Run 的受控范围。

### 3. 图片理解与安全暂存

项目素材主要保存在浏览器本地，Go Worker 不能直接读取。启动分镜提示词阶段前，前端按当前场次 / 生成批次的资产引用解析图片，先创建一个绑定登录用户、workflow、stage 和启动幂等键的上传批次，再把图片上传到该批次。启动接口只接收批次 ID；后端创建 Agent Run 时原子地占用批次并补充 run 绑定，避免出现“任务尚未创建却需要 run ID”的循环依赖。

- 选择优先级固定为主角色、主场景、关键道具、补充造型；最多 9 张，与 Seedance 参考图上限一致。
- 每张图片同时记录 `assetId`、名称、类型、版本、顺序和内容指纹；运行详情只返回这些业务字段，不返回服务端绝对路径。
- 后端校验用户归属、数量、大小、扩展名、MIME 和真实文件签名，只写入服务端配置的暂存根目录。
- Agent Run 入队前必须原子占用批次并冻结图片清单；同一批次不能被另一个任务复用，CLI 使用重复的 `-i` 参数读取这些文件。
- 任务重试复用同一版本清单；终态超过保留期后自动清理。取消或失败不会删除浏览器素材。
- 有引用但文件缺失、损坏或上传失败时阻断启动，并显示具体缺失项；镜头本来没有图片引用时允许继续，但运行记录明确标记“纯文本降级”，不能静默发生。
- 测试占位图必须包含可被视觉模型辨识的角色、场景或道具信息，禁止使用纯色空白图冒充图像理解验收。

### 4. 任务创建与计费

API 模式维持当前行为：创建任务时解析后台文本模型与渠道，计算预估算力点；Worker 领取后预扣，失败按现有规则退款。

Codex CLI 模式不要求后台存在文本模型渠道，任务记录使用：

- `Executor=codex-cli`
- `Provider=local-codex-cli`
- `Protocol=codex-cli`
- `Model=WORKFLOW_CODEX_MODEL`，未指定时显示“当前 Codex 登录态”
- `EstimatedCredits=0`、`Credits=0`

CLI 模式不操作应用算力点账本，但保留耗时、尝试次数、错误、状态、artifact 和审核记录。CLI 失败仍走同一停止 / 重试状态机，不自动回退 API；API 模式也不自动回退 CLI。

### 5. 健康状态与页面表达

Worker 健康接口增加 `executor` 与 `executorLabel`。API 模式检查文本渠道可用性；CLI 模式检查：

- 当前不是生产环境；
- 本地开关已开启；
- `codex` 可执行文件可定位；
- 固定工作目录存在；
- `codex --version` 能在短超时内完成。

统一工作台仍只展示只读摘要：本地显示“Codex CLI（本地验证）”，生产显示后台 API 模型。分镜任务详情显示本次参与理解的图片数量、名称、类型、版本和顺序；页面不提供执行器切换、路径、登录态、密钥或命令参数编辑。

### 6. 本地运行方式

Codex CLI 依赖宿主机登录态，因此推荐用宿主机启动 Go API 与 Next.js 开发服务：

```dotenv
APP_ENV=development
WORKFLOW_TEXT_EXECUTOR=codex-cli
WORKFLOW_LOCAL_CODEX_ENABLED=true
WORKFLOW_CODEX_BIN=codex
WORKFLOW_CODEX_WORKDIR=/absolute/path/to/infinite-canvas-main
# 可选：WORKFLOW_CODEX_MODEL=<model>
```

`docker-compose.local.yml` 继续保持 API 模式，不挂载宿主机 Codex 凭证和二进制，避免把个人登录态复制进容器。需要验证 Docker 上线形态时，使用当前 API / Worker 路径。

### 7. 后台工作流 Skill 版本中心

六个稳定阶段键 `script`、`art`、`assets`、`storyboard`、`video`、`delivery` 都预留 Skill 绑定。每个阶段绑定一个“Skill 包”，包内可以包含主 `SKILL.md`、模板、规则、示例和输出说明；后台更新 Skill 不再要求重新构建前端或发布整站。

Skill 数据分为三层：

- `WorkflowSkill`：稳定 ID、名称、用途、适用阶段和启用状态。
- `WorkflowSkillVersion`：不可变版本号、状态、文件清单、主内容、manifest、内容哈希、创建人和发布时间。状态只允许 `draft`、`published`、`archived`。
- `WorkflowStageSkillBinding`：阶段键、当前发布版本 ID 和更新时间。同一阶段任一时刻只有一个生效 Skill 包。

内置 Skill 在首次启动时幂等导入为初始发布版本，数据库版本成为运行时唯一来源；代码内置内容只负责初始化和数据库为空时的恢复，不再直接决定新任务提示词。

后台新增独立页面 `/admin/workflow-skills`，不放进模型设置。页面提供：

- 六阶段绑定总览、当前版本、内容哈希、发布时间和最近使用情况；
- 新建 Skill、从已发布版本创建草稿、编辑主说明和附属文本文件；
- 校验草稿、发布新版本、切换阶段绑定和回滚到历史发布版本；
- 版本差异、引用该版本的运行次数和正在执行的任务数量；
- 草稿预览，但草稿不能绑定阶段或进入生产任务。

第一版只接收 Markdown / JSON 文本文件，不接收 zip 或任意可执行文件，避免压缩包路径穿越和脚本执行。单文件、单版本和文件数量都有服务端限制；文件名经过规范化，只允许相对逻辑路径。

管理员 API：

- `GET/POST /api/v1/admin/workflow-skills`
- `GET/PATCH /api/v1/admin/workflow-skills/:id`
- `POST /api/v1/admin/workflow-skills/:id/versions`
- `GET /api/v1/admin/workflow-skill-versions/:id`
- `POST /api/v1/admin/workflow-skill-versions/:id/validate`
- `POST /api/v1/admin/workflow-skill-versions/:id/publish`
- `GET/PUT /api/v1/admin/workflow-stage-skill-bindings/:stageKey`

普通用户不能读取草稿或修改绑定。工作流详情只返回 Skill 名称、版本和哈希等可审计摘要，不返回后台草稿。

### 8. Skill 解析与任务快照

阶段启动时，服务端读取该阶段当前绑定的已发布版本，并把规范化后的 Skill 内容加入 Worker 提示词。结构化质量门仍由服务端代码执行，Skill 文本不能关闭权限、审核、计费、图片限制或质量门。

`AgentRun` 冻结 `SkillID`、`SkillVersionID`、`SkillVersion`、`SkillContentHash` 和规范化 `SkillSnapshotJSON`。任务入队后发布或回滚 Skill 不会改变该任务；新启动的任务使用最新绑定。停止后重试默认复用原任务的 Skill 快照，主动发起“使用最新 Skill 重跑”才创建新任务和新快照。

发布采用事务：校验版本 → 将版本标记为 published → 更新阶段绑定 → 写入管理员审计记录。发布失败时旧绑定保持不变。历史发布版本不可编辑；回滚只是把阶段绑定重新指向旧发布版本，不复制或覆盖历史内容。

阶段 Skill 的用途按阶段约束：

- `script`、`art`、`storyboard`：直接参与文本 / 多模态 Agent 提示词。
- `assets`：约束资产映射、缺图判断和图片理解清单。
- `video`：约束提示词预检、参考图顺序与最低成本测试规则，不能绕过付费确认。
- `delivery`：约束交付检查清单，不能降低代码级硬门禁。

## 数据流

1. 用户在统一工作台启动阶段。
2. 服务端解析该阶段当前绑定的已发布 Skill；不存在有效版本时阻断启动。
3. 分镜提示词阶段由前端解析当前场次 / 生成批次的图片，按固定优先级上传最多 9 张参考图，并取得一次性批次 ID。
4. 后端根据启动时已经验证的执行器模式创建 Agent Run，冻结 `Executor`、Skill 版本快照与图片清单。
5. Worker 领取任务并续租；API 任务选择后台渠道并计费，CLI 任务通过 `-i` 附加暂存图片并启动受控子进程，且不计应用算力点。
6. 两种执行器都返回同一格式的文本与结构化草案，artifact 记录 Skill 哈希与图片引用业务元数据。
7. 现有质量门、审核哈希、映射预览、应用本地和回执流程继续执行。
8. 停止、超时、重试、刷新恢复和服务退出使用同一状态机。

## 错误处理

- 未安装 CLI：健康状态显示不可用，任务启动前返回“本地未找到 Codex CLI”。
- 未登录或 CLI 返回非零：保存安全化错误摘要，任务进入失败；不回退 API。
- 超时 / 取消：终止子进程并按现有规则进入失败或已停止。
- 输出为空：按可重试上游错误处理。
- 输出不是 JSON：保留 `RawOutput`，沿用现有文本解析和人工审核能力。
- 引用图缺失或损坏：有引用时阻断任务创建并列出缺失项；无引用时记录显式降级状态。
- 阶段没有已发布 Skill：阻断启动并提示管理员配置，不回退前端硬编码版本。
- Skill 发布校验失败：草稿保留，旧发布版本和阶段绑定不变。
- 运行中发布新版本：当前任务继续使用冻结快照，新任务才读取新版本。
- 生产误配置：服务启动失败，不等待第一个任务才发现风险。

## 测试与验收

### 自动测试

- 配置：开发环境显式开启成功；默认使用 API；四种生产环境标记均拒绝 CLI；CLI 路径和工作目录只从服务端读取。
- 任务：CLI 模式无需模型渠道、费用为零、任务记录执行器；API 模式行为和计费不变。
- 图片暂存：用户隔离、workflow / stage / run 绑定、图片签名、数量和大小限制、顺序、版本指纹、重试复用、终态清理、缺图阻断和无图显式降级。
- 执行器：成功、空输出、非零退出、超时、取消、临时文件清理、stderr 截断、模型参数可选、固定只读参数，以及 1 / 3 / 9 张图片的 `-i` 顺序。
- Worker：CLI 成功进入待审核并生成 artifact；失败 / 停止 / 重试 / 租约恢复保持一致；API 回归全部通过。
- 健康：分别报告 API 与 CLI 可用性，不暴露本地绝对路径和登录凭证。
- Skill API：管理员鉴权、草稿隔离、校验、不可变发布、事务绑定、回滚、六阶段键约束、文件限制、内容哈希和审计记录。
- Skill 快照：发布后新任务使用新版本，运行中任务和普通重试保持旧版本，“使用最新 Skill 重跑”创建新快照。
- 后台页面：六阶段总览、版本编辑、差异、发布、绑定和回滚主路径，以及非管理员拒绝访问。

### 真实本地验收

先在后台为导演与美术阶段发布一个仅用于验收的新 Skill 版本并切换绑定。使用宿主机 Codex 登录态，从统一页面完成一次导演与美术阶段和一次带参考图的分镜提示词阶段，检查新任务是否使用已发布 Skill、CLI 是否基于图片可见内容生成提示词，并核对队列、Skill 版本、图片清单、日志、质量门、审核、资产 / 生产包映射、刷新恢复、停止与重试。运行期间再发布下一版 Skill，确认当前任务不变、新任务才使用新版本；最后回滚绑定。该验收可能消耗 Codex 账户额度，但不扣应用算力点。

完成文本与图片理解链路后，执行一次企业视频 API 最低消耗冒烟：先做不扣费预检，只提交一条已确认生产包，选择后台可用的最低成本模型、最低分辨率、最短允许时长并关闭音频。提交前再次显示实际模型、参数和预估成本；余额异常、预检失败或参数被上游抬高时停止，不创建任务。成功后验证任务同步、视频回填、历史版本和素材归档，不重复提交第二条付费任务。

### 上线门禁

- 生产配置加载测试必须拒绝 CLI。
- `docker-compose.yml`、`docker-compose.local.yml` 和 `.env.example` 的部署示例保持 API 模式。
- 生产镜像确认没有 `codex` 可执行文件。
- Docker 内创建 CLI 类型任务必须被拒绝；API Worker 健康、队列和主路径继续通过。
- 发布前扫描用户界面，不能出现执行器切换、CLI 路径或本地凭证配置。
- 发布验收报告必须分别标记 Codex CLI 多模态验证和企业视频 API 付费冒烟，不能把测试占位图写成真实图片模型产物。
- 每个阶段必须绑定一个有效发布 Skill；生产任务必须记录版本与哈希，后台草稿和已归档版本不能被执行。

## 不做事项

- 不恢复旧 `/original-workflow` 本地文件 Runner、`.workflow-cache`、Python 脚本或 Next API 执行链。
- 不允许浏览器指定 `codex-cli`、命令、工作目录或执行参数。
- 不允许浏览器上传后再指定任意服务端图片路径。
- 不把 Codex CLI 当作生产 fallback。
- 不让 CLI 直接修改素材、分镜、画布或数据库。
- 不允许 Skill 内容覆盖鉴权、计费、图片限制、质量门或人工确认等代码级安全规则。
- 不允许直接编辑已发布版本，或用文件系统覆盖数据库中的活动版本。
- 不用 CLI 替代真实视频渠道或声称视频付费链路已经被验证。
