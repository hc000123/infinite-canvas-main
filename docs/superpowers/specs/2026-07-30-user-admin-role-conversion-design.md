# 普通用户与管理员角色转换设计

## 背景

当前普通用户管理与管理员管理是两条相互隔离的链路：普通用户保存接口强制角色为 `user`，管理员编辑接口又只接受已存在的 `admin` / `superadmin`。因此系统没有合法入口把已创建的普通用户提升为管理员。

## 目标

- 超级管理员可以把现有普通用户提升为普通管理员。
- 超级管理员可以把普通管理员降级为普通用户。
- 转换前后保留同一个账号 ID、用户名、密码、资料、算力余额、历史用量、算力流水、操作记录和登录记录。
- 普通管理员和普通用户不能执行角色转换。
- 角色变更留下包含操作者、目标账号、前后角色、请求 IP 和时间的安全审计记录。

## 非目标

- 不允许通过普通用户编辑接口提交管理员角色。
- 不在本入口创建或删除账号。
- 不通过本入口提升或降级超级管理员；超级管理员仍沿用现有管理员编辑和最后一个有效超级管理员保护规则。
- 不重置余额、密码、工作 IP 白名单或 IP 审批开关。

## 方案

采用管理员管理页内的专用角色转换入口。

### 后端

新增超级管理员专用接口 `POST /api/admin/admins/:id/role`，请求体只接受：

```json
{ "role": "admin" }
```

或：

```json
{ "role": "user" }
```

服务层必须根据数据库重新读取操作者和目标账号，不能只信任令牌中的角色。合法状态转换仅有：

- `user → admin`
- `admin → user`

目标不存在、角色未变化、转换方向非法、操作者不再是有效超级管理员时返回明确错误。超级管理员不能通过该接口修改自己，也不能把任何账号转换为 `superadmin`。

仓储层在单个数据库事务内锁定并重新读取操作者和目标，只更新目标的 `role` 与 `updated_at`，同时写入一条 `security.admin_role_changed` 安全活动记录。活动记录归属目标账号，以便该账号降级后仍能在用户详情中看到；元数据保存 `actorId`、`fromRole`、`toRole`，IP、会话和设备信息取自服务端请求上下文。

### 前端

超级管理员的“管理员管理”页新增“提升现有用户”按钮。点击后打开可搜索选择框，通过现有普通用户列表接口按关键词查询；选中用户后显示账号、当前算力余额，并二次确认提升。成功后同时刷新管理员列表和普通用户列表缓存。

普通管理员行新增“降为普通用户”操作。确认弹窗明确提示账号资料、余额和历史记录均会保留；成功后该账号从管理员列表移除并重新出现在普通用户列表。超级管理员行不显示降级入口。

### 角色与算力行为

- 提升后账号成为普通管理员，继续持有并消耗原有真实算力余额。
- 普通管理员可按现有规则把自己的额度转移给普通用户，但不能调整自己的额度。
- 降级后账号继续使用转换时的余额，按普通用户规则消费。
- 只有超级管理员免余额限制。
- 管理员角色继续绕过普通用户 IP 审批；降级后原有 IP 审批配置重新按普通用户规则生效，因为相关字段不被清除。

## 错误与并发

- 事务内再次校验操作者和目标角色，避免两个页面同时转换造成越权或覆盖。
- 使用条件更新确保目标仍处于预期旧角色；角色已经变化时提示刷新后重试。
- 角色更新或审计写入任一步失败时整体回滚。
- 前端提交期间禁用重复确认，后端仍以事务校验作为最终边界。

## 验收标准

1. 超级管理员可搜索现有普通用户并提升为管理员。
2. 提升后账号出现在管理员列表，且 ID、余额、密码哈希、资料和历史数据未改变。
3. 超级管理员可将普通管理员降为普通用户，数据同样保留。
4. 普通管理员无法调用接口；令牌角色过期但数据库已降权的操作者同样失败。
5. 无法转换超级管理员、自己、已处于目标角色或不合法角色。
6. 每次成功转换只有一条安全审计，包含目标账号、操作者、前后角色和请求来源信息。
7. 普通用户保存接口仍拒绝伪造管理员角色。
