# 工作流 Skill 生产化重建设计

## 背景

当前六阶段工作流 Skill 版本中心已经具备数据库版本、任务快照、项目灰度、全局绑定、评测、回滚和审计能力，但系统内置 `2.0.2` 版本只有一段简短 `SKILL.md`。所有阶段的输出契约均为 `{"type":"object"}`，运行时也只把 `SKILL.md` 加入系统提示词，后台允许维护的规则、模板和示例文件不会参与执行。

本次以 `/Users/huangchi/Desktop/Seedance 分镜师 2.0 - codex 版/` 为专业知识来源。该目录包含 17 个 Skill、模板、参考资料和示例，覆盖剧本拆解、人物/场景/道具设计、运镜、表演、灯光、声音、分镜、运动提示词、审核和渲染执行。原目录面向本地 Codex 文件工作流，不能直接复制到当前云端 Worker：其中包含本地目录、MCP、Hook、`/goal`、自进化、Suno、ElevenLabs 和即梦 CLI 指令，阶段顺序和最终输出格式也与当前产品不同。

## 目标

- 保持 `script`、`art`、`assets`、`storyboard`、`video`、`delivery` 六个稳定阶段键不变。
- 保持现有项目分集工作流页面、五个运行阶段和四个 AI 阶段不变。
- 把外部目录中的专业方法提炼为六个可版本化、可评测、可回滚的生产 Skill 包。
- 让包内规则、模板和示例真正进入模型上下文，不再只是后台可见文件。
- 让输出 JSON Schema、必需输入和图片策略参与实际运行校验。
- 继续由服务端硬质量门负责权限、审核、ID、引用、时长和连续性约束，Skill 文本不能关闭这些门禁。

## 非目标

- 不重做工作流状态机，不新增用户可见阶段。
- 不把外部文件夹复制进项目，也不运行其中的 Hook、MCP 或 CLI。
- 不在本次接入音频生成、批量出图或即梦 CLI。
- 不引入 `/goal`、自进化、自动创建 Skill 或子 Agent 编排。
- 不改变当前画布、素材库和视频生成的数据落点。

## 方案选择

采用“专业内容精选重组 + 现有运行链路补强”。不采用原样复制，因为外部指令依赖不存在的本地执行环境；不采用状态机重做，因为它会同时改变页面、阶段依赖、产物结构和用户验收范围。

外部内容只作为专业方法来源。进入当前项目后，所有规则必须改写为云端 Worker 可执行的纯文本指令，并服从当前 JSON 产物、前端字段和服务端质量门。

## Skill 包结构

新增后端内嵌资源目录：

```text
service/workflow_skill_seeds/
├── script/
│   ├── SKILL.md
│   ├── rules/domain-rules.md
│   ├── templates/output-template.md
│   └── examples/good-output.json
├── art/
├── assets/
├── storyboard/
├── video/
└── delivery/
```

每个目录是一个完整版本包：

- `SKILL.md`：阶段目标、判断顺序、执行边界、禁止事项和附属文件用途。
- `rules/domain-rules.md`：从外部 Skill 提炼的专业规则。
- `templates/output-template.md`：输出字段含义和生成顺序，不替代 JSON Schema。
- `examples/good-output.json`：与当前项目字段完全一致的最小优质样例，不复制外部示例剧情。

种子加载使用 `go:embed`，不在 Go 字符串常量中维护大段 Skill 正文。首次启动或发现新内置版本时，把嵌入文件规范化后写入 `WorkflowSkillVersion.FilesJSON`，数据库仍是运行时唯一来源。新版本号为 `3.0.0`；旧发布版本保留用于审计和回滚。

## 六阶段能力映射

### `script`：生产剧本确认

吸收 `script-breakdown` 的事实保留、场次边界、剧情点完整性和生产可读性规则。输出继续以 `productionScript` 为唯一必需字段，不在本次新增自动剧本改写阶段。该包用于版本中心、评测和未来脚本阶段扩展；现有已确认剧本仍由系统创建并批准。

### `art`：资产提取

吸收 `script-breakdown` 的人物、场景、道具入表标准和证据纪律。只从剧本提取：

- `character`：需要跨镜保持身份一致的角色。
- `scene`：需要稳定空间、时段、光向和关键陈设的场景。
- `prop`：跨镜复现、承担叙事功能或需要独立参考图的关键道具。
- `costume`：服装、发型、妆容、年龄阶段和伤势等角色外观变体。

继续使用 `CHAR-001`、`SCENE-001`、`PROP-001`、`COSTUME-001` 稳定编号。每项必须包含剧本原文证据和可见描述；证据不足时不得猜测。`costume` 必须绑定当前产物中的父角色，并保留变体类型和名称。本阶段不得生成 `imagePrompt`。

### `assets`：资产生图提示词

吸收 `character-design`、`scene-design` 和 `prop-design`：

- 角色：同一人四视设定图，面部特写与全身正/侧/背同图，白底，身份一致。
- 场景：单张干净主参考图，以能立住空间结构、纵深、光向和关键陈设的建场机位为准，不使用宫格拼贴。
- 道具：四视或适合结构识别的白底设定图，写清材质、尺寸、磨损和功能状态。
- 角色马甲：继承父角色身份，只描述外观变化，不重新发明人物。

所有项目保持上游 ID、名称、证据、描述和变体关系，不增删、不合并、不重编号。各项输出 `imagePrompt` 和 `status=ready`。同一批次的提示词共享一致的画风、材质和光线口径，但不得虚构剧本没有提供的身份事实。

### `storyboard`：结构化分镜拆解

吸收 `script-breakdown`、`storyboard`、`camera`、`performance`、`lighting` 和 `sound-design` 的镜头方法，但输出必须服从当前 `WorkflowShotDraft`：

- 每条是一个 4–15 秒生成单元，只承担一个叙事目的。
- 时长由事件、台词和反应气口决定，不默认填满 15 秒。
- 一个主运镜；机位、景别和运动方向明确，避免堆叠互相冲突的镜头运动。
- 动作用可拍摄的物理动作链；表演落到眼神、呼吸、下颌、肩线、手指和重心等可见变化。
- 台词逐字保留；对白长度服从当前时长承载能力。
- `continuous` 只用于同一时空、同一动作或情绪状态的连续发展，其余使用 `cut`。

输出继续为 `shots[].shotId/sceneKey/sourceScript/shotDraft`，`shotDraft` 只包含当前前端支持的 `shotSize/camera/movement/action/performance/dialogue/durationSeconds/continuityMode`。专业灯光、声音和调度要求写入这些现有字段的自然语言，不扩张前端数据结构。

### `video`：单镜头多模态提示词

吸收 `motion-prompt` 的可跟随性、单一主运镜、物理动作、参考素材职责绑定和失败降复杂度规则。输出保持当前合同：

- `shotId`
- `prompt`
- `promptInputHash`
- `referenceEvidence[]`

最终 `prompt` 必须包含“场景：”“声音：”“画面内容：”“限制：”和连续时间段。外部目录“不写秒数”的建议不适用于当前项目。

实际参考图片按当前请求顺序使用 `@图1` 至 `@图N`，不输出外部目录的 `@char-001`、`@scene-001` 文件引用。每张图在 `referenceEvidence` 中记录 `imageRef/observations/appliedTo`；提示词只保留与当前镜头相关的身份、场景、道具或走位职责，避免重复描述参考图已经锁定的静态外观。

上一镜尾帧只能作为 `continuity_reference` 普通参考图。本镜从该画面之后继续发展，保持场景、角色身份、服装、光线、材质与画风一致；不得标记为首帧、不得要求第一帧复刻、不得重新诠释视觉设定。

### `delivery`：成片交付

吸收 `review` 与三类 manifest 的可追溯思想，只定义交付检查，不执行外部工具。输出汇总成功项、失败项、失败原因、重试建议、素材引用完整性和导出清单。当前状态机不启动该 Agent；包先进入版本中心和评测体系，为后续正式交付阶段预留稳定契约。

## 运行时加载

当前 `workflowSkillInstructions` 只读取 `SKILL.md`。改为按以下确定顺序合成上下文：

1. `SKILL.md`
2. `rules/` 下文件，按逻辑路径排序
3. `templates/` 下文件，按逻辑路径排序
4. `examples/` 下文件，按逻辑路径排序
5. 其余允许文件，按逻辑路径排序

每个文件用清晰边界标记包裹，包含逻辑路径，避免模型把示例误认成当前输入。任务快照继续冻结完整文件 Map、契约和内容哈希；重试从快照按同一算法重建提示词。

文件规则：

- 只允许 `.md` 和 `.json`。
- `SKILL.md` 必须存在且非空。
- 单文件最多 64 KiB。
- 单包最多 128 KiB、32 个文件。
- JSON 文件保存时必须能解析。
- 继续拒绝绝对路径、目录穿越和可执行文件。

## 契约与质量门

每个内置包保存具体 JSON Schema，不再使用空对象 Schema。使用成熟 JSON Schema 库编译和验证，不手写通用 Schema 解析器。

校验分三层：

1. 草稿保存：检查文件、Schema 语法、契约字段和阶段兼容性。
2. 阶段启动：检查 `requiredInputs`、图片数量、图片格式、是否允许无图降级。
3. 阶段完成：先校验输出 JSON Schema，再执行现有阶段硬质量门和跨产物身份校验。

JSON Schema 失败作为阻断问题写入质量门报告，产物仍可保存用于诊断，但不能批准。阶段硬质量门按阶段固定执行，不能通过删除 `qualityGateProfile` 关闭。`qualityGateProfile` 只能声明该 Skill 需要的附加门，并且必须包含当前阶段的强制门。

图片批次在创建 Agent Run 时已经生成冻结 manifest。启动阶段根据 manifest 实际数量和 MIME 校验 `min/max/allowedTypes`；`required=true` 时禁止空批次，`allowTextFallback=false` 时缺图直接阻断。

## 硬编码提示词边界

保留短小的系统级基础提示词，负责角色身份、只输出 JSON、当前阶段和安全边界。具体业务方法、字段解释、正反例和写作规则全部进入 Skill 包，避免两份长提示词互相覆盖。

服务端仍硬编码且不可被 Skill 覆盖的内容：

- 权限、计费、人工审核和应用回执。
- 稳定 ID、图片上限、时长范围和引用证据。
- 输入哈希回写和跨产物身份保持。
- `continuity_reference` 不得作为首帧的规则。

## 版本与数据库行为

新内置版本为 `3.0.0`，创建人为 `system`。启动时：

- 缺少 `3.0.0` 时创建，不修改旧版本正文。
- 当前全局绑定仍指向系统内置旧版本时，自动升级到 `3.0.0`。
- 当前绑定指向管理员发布的自定义版本时保持不变。
- 历史 `1.0.0`、`2.0.1`、`2.0.2` 保留，可通过版本中心回滚。

## 错误处理

- 内嵌包缺文件、JSON 无效或超过体积限制：后端启动种子导入失败，错误包含阶段键和逻辑路径。
- 管理员草稿引用非法文件：保存失败，不产生半成品版本。
- 运行时快照损坏：拒绝启动或重试，不回退到当前最新版，避免任务内容漂移。
- Schema 编译失败：版本不能发布。
- 输出 Schema 不通过：质量门报告列出 JSON 路径和原因，不能人工批准。
- 图片策略不通过：阶段启动前返回明确中文错误，不创建计费任务。

## 测试策略

按照测试先行实现：

1. 种子测试：六阶段 `3.0.0` 均包含多文件、严格 Schema 和阶段专属规则；系统绑定升级、自定义绑定不覆盖。
2. 包校验测试：拒绝未知扩展名、非法 JSON、单文件超限、整包超限和路径穿越。
3. 上下文测试：所有附属文件按确定顺序进入提示词，快照重试结果一致，示例带文件边界。
4. 契约测试：缺必需输入、图片数量不足/过多、MIME 不允许时在创建任务前失败。
5. Schema 测试：四个运行阶段的合法样例通过，缺字段、错类型、非法枚举和超限数组失败。
6. 质量门回归：稳定 ID、变体父角色、分镜时长、台词预算、输入哈希、逐图证据和尾帧连续性规则继续有效。
7. 前端兼容测试：分镜解析继续只依赖现有八个 `WorkflowShotDraft` 字段，资产卡和提示词审核无需改页面结构。

项目规范默认不执行完整构建。本次涉及核心工作流契约，实施阶段运行有针对性的 Go 测试和现有相关前端单元测试，不做无关全量构建。

## 验收标准

- 管理后台六阶段当前系统版本均为 `3.0.0`，每个版本至少包含主说明、规则、模板和样例。
- 新任务请求中包含当前包的所有运行时文件，任务快照和内容哈希可审计。
- 四个 AI 阶段输出均通过对应 JSON Schema 和硬质量门后才可批准。
- 外部目录的本地路径、MCP、Hook、`/goal`、自进化和 CLI 指令不出现在生产 Skill 中。
- 视频 Skill 明确执行 `continuity_reference` 规则，不把上一镜尾帧当首帧。
- 现有工作流页面、资产卡、分镜编辑和视频提示词审核流程保持可用。
